# AI 角色化 UI/UX 评审清单

## 一、口径声明（必须照抄）

当前会话已启用 UI/UX 专家时，在评审文档开头写明专家名称与启用状态。

未启用 UI/UX 专家时，`05-ux-review.md` 的标题与正文首段必须写：

> 本次为 **AI 角色化 UI/UX 评审**（未启用 UI/UX 专家，非真人或外部专家意见），依据下列清单对选定风格稿做结构化自检，不构成真实专家评审或真实用户测试结论。

禁止使用「专家一致认为」「用户调研显示」「行业最佳实践要求」等表述。涉及现行平台规范或可访问性标准时先核对该平台公开文档并记录依据链接，区分「硬约束」与「建议」。

## 二、评审输入

- 选定的首页风格稿（HTML + PNG）
- `01-entry-check.md` 锁定的页面清单与范围
- `PRD.md` 中该页的业务目标、状态与验收标准（只读）
- `04-style-decision.md` 中用户保留的局部偏好

## 三、检查项

| 类别 | 检查点 | 判定依据 | 分级 |
|---|---|---|---|
| 需求吻合 | 页面元素、文案、状态是否与原型一致；有无因视觉调整删减信息 | 与 `PRD.md`、原型首页逐项比对 | 硬约束 |
| 视觉层级 | 主任务是否第一眼可见；标题/数值/操作的主次是否清晰 | 首屏视线与字号字重阶梯 | 建议 |
| 信息密度 | 单位屏信息组数是否与产品形态匹配；有无拥挤或空洞 | 密度档位与分组数 | 建议 |
| 可读性与对比度 | 正文与背景、次要文字、禁用态是否达到基本可读性；小字号是否过大面积使用 | 对比度计算与字号下限 | 硬约束 |
| 可访问性 | 关键操作是否键盘可达、可聚焦；文字与图标是否可朗读；是否只靠颜色传达状态 | 可聚焦元素、文案冗余 | 硬约束 |
| 状态完整性 | 空 / 加载 / 错误 / 成功 / 无权限 / 超长文本 / 超量数据 是否都有表达 | 状态清单 | 硬约束 |
| 一致性 | 同类控件在不同位置是否同形同色；间距是否落入已定义档位 | token 快照 | 硬约束 |
| 操作成本 | 核心任务关键操作步数；危险操作是否有确认；是否可返回 | 任务路径 | 建议 |
| 实现成本 | 是否引入难以稳定实现的渐变、模糊、异形裁切 | 技术常识，标「推导」 | 建议 |
| 规范可抽取性 | 每个视觉决策能否写成可判定规则；不能的那部分登记为待观察项 | 四要素检验 | 硬约束 |

## 四、输出格式

```markdown
### 评审项 RX-01
- 类别 / 检查点：
- 观察：（只写可见事实）
- 判定：通过 / 需修订 / 待用户决策
- 分级：硬约束 / 建议 / 偏好
- 依据：（清单条目、对比度数值、PRD 章节或平台文档链接）
- 建议：（可执行、说明落到哪个 token 或页面）
- 修订落点：（design-spec 章节 / token 字段 / 候选稿 / 登记为遗留）
```

## 五、冲突裁决序

当不同视角意见冲突时，按顺序裁决并记录理由：

**需求一致性与硬约束 > 可访问性与可读性 > 全局一致性 > 实现成本 > 审美偏好**

- 审美偏好与可访问性冲突时，可访问性优先，成本让步。
- 判定条件不可测的规范不得进入 `design-spec.md`。
- 需要用户取舍的只提交「硬约束无法满足」或「两个方案代价相当」两类，专业问题自行收敛。

## 六、收敛

单轮评审聚焦不超过 10 条意见，每条标注采纳 / 部分采纳 / 拒绝及理由。修订只改被点名范围，保留未要求改动的内容。无法收敛的记入遗留问题，不阻塞主流程，但必须进 `08-design-acceptance.md`。

## 七、自检

- [ ] 口径声明完整，未冒充真人或外部专家
- [ ] 每条意见有依据与修订落点，无「体验更好」类不可判定表述
- [ ] 硬约束项全部通过或有明确处置
- [ ] 未把行业惯例写成强制标准
- [ ] 无绝对化用语与违禁词
