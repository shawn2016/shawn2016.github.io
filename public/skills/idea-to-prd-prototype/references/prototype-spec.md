# 两阶段 HTML 原型规范

## 共同要求

- 根据当前 PRD 和已确认决策制作，不得擅自增加功能。
- 将 PRD 未明确的内容标为「待确认」，不得自行补全。
- 输出可直接打开的单文件 HTML，将 CSS 和 JavaScript 内联，无构建步骤、后端或外部依赖。
- 使用语义化 HTML、可辨识按钮和键盘可达的基础导航。
- 在文件内记录原型版本、关联 PRD 版本和页面索引。
- 页面或状态使用 `PG-001`、`ST-001` 等稳定编号，与 PRD 追溯表一致。
- 完成后使用 `present_files` 打开，不只提供代码块或文件路径。
- 原型用于需求验证，不是生产代码，不开展品牌视觉或设计系统深化。

## 第一阶段：低保真线框 HTML

### 目的

快速检查页面完整性、信息层级、页面关系和核心流程，帮助用户发现 PRD 问题。不要让用户评价颜色、字体或视觉美丑。

### 视觉表达

- 仅使用黑、白、灰、基础框线、按钮轮廓和图片占位块。
- 只表达信息层级、核心文案、按钮位置、页面结构和页面状态。
- 不使用正式配色、品牌设计、复杂动画、阴影或精细组件视觉。

### 导航结构

采用「幻灯片式流程导览 + 页面内点击跳转 + 简单页面索引」：

1. 默认每次只展示一个页面或状态，不将长页面作为所有屏幕的简单容器。
2. 顶部显示页面名称、页面编号、当前步骤和总步骤。
3. 提供上一步、下一步和页面目录；由用户手动控制，不自动播放。
4. 主要按钮和入口支持点击，并跳转到 PRD 对应目标。
5. 提供返回路径，避免进入分支后无法回到主流程。
6. 提供简单流程总览或页面目录，用于检查页面完整性并直接跳转。
7. 不允许流程引用不存在的目标页面；目标不明确时标为「待确认」。

### 每屏信息

- 页面名称及编号
- 在流程中的位置
- 用户进入此页面的目的
- 主要内容和操作
- 操作后进入的页面或状态
- 当前页面的待确认事项

### 页面和状态

- 按真实使用顺序组织主流程。
- 覆盖 PRD 中全部核心页面和关键状态。
- 将首次使用、权限申请、加载中、无数据、失败和异常恢复作为相关页面的状态变体。
- 不将分支和异常强行排列成一条虚假线性流程。
- 文件末尾提供「待确认清单」。

### 用户检查方式

给用户一条主流程和必要分支，让用户实际点击。只收集四类反馈：

1. 页面是否缺失。
2. 流程顺序是否正确。
3. 点击目标是否符合预期。
4. 页面内容和操作是否符合理解。

将反馈同步修回 PRD。用户明确确认主流程后，才能进入完整可操作原型。

## 第二阶段：完整可操作 HTML 原型

### 目的

让用户通过接近真实使用的操作判断产品是否符合预期，形成最终需求验证基线。此阶段仍不是最终视觉设计或正式开发。

### 交互覆盖

- 完整的导航、返回、页面跳转和核心任务链路。
- 关键表单输入、校验、提交、取消和重复提交防护表现。
- 弹窗、提示、确认、撤销和必要的状态切换。
- 成功、失败、空数据、加载、无权限和异常恢复。
- 不同角色或权限导致的核心差异（如适用）。
- 接近真实场景的文案和模拟数据，不使用无意义的 lorem ipsum。
- 对模拟行为明确标注，避免让用户误以为已连接真实数据。

### 保真度边界

使用清晰、统一、可操作的界面表达信息层级和交互意图，可以比线框阶段更完整，但不进行品牌探索、复杂视觉设计、设计令牌或生产组件库建设。将纯视觉偏好记录给后续设计 Skill。

### 任务式体验

根据 P0 需求选择三至五个核心任务。每个任务包含：

```text
任务编号：TASK-001
用户目标：<用户要完成的事情>
起点：<页面或状态>
操作路径：<由用户实际完成>
预期结果：<可观察结果>
关联需求：REQ-...
```

不要只问「有没有问题」。让用户完成任务后，逐项记录：

- 符合预期
- 不符合预期的具体步骤
- 用户期望的行为
- 是否需要修改 PRD
- 处理结果及回归结果

### 修改与回归

- 同时修改原型、PRD、验收标准和追溯表。
- 仅重新体验受影响任务及关联路径。
- 若改变目标用户、核心问题或 P0 范围，返回早期对应阶段。
- 不因视觉偏好无限延长当前阶段。

## 最终原型自检

- 文件可离线打开，无外部资源依赖。
- 所有 P0 核心流程均可从入口走到成功终点。
- 主要按钮均有目标或明确「待确认」标记。
- 分支可以进入并返回，没有孤立页面。
- 表单及状态反馈与 PRD 一致。
- 页面编号与 PRD 追溯表一致。
- 模拟数据和模拟行为已明确标识。
- 不包含生产密钥、真实个人隐私数据或真实后端写操作。
