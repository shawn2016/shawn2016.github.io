# 可复用提示词

分两类：A 类给用户直接粘贴在任务前后；B 类给智能体用于把任意任务重写成深度版。

---

## A. 用户侧提示词

### A1. 深度版（最常用，贴在任务后面）

> 我要这个任务的更深版本，不是更大版本。动手前先回答：
> (1) 这个领域顶尖的专业人士会做哪些我没要求的事？
> (2) 他们会从什么最原始的材料入手，而不是别人已消化过的二手材料？
> (3) 他们会用哪些具体方法和工具？
> (4) 除了你和我，什么能证明结果是对的？
> 然后按这四点重写任务并执行。

### A2. 升高度（用于反复出现、需要人盯的问题）

> 先别只做我字面说的这一步。告诉我：这件事完成之后我接下来要做什么？那个下一步能不能一起解决？如果这类问题以后还会发生，给一个让它不再发生的机制方案，和只修本次的方案做对比，说明各自代价，再让我选。

### A3. 要求方案比较（防止只给一条路径）

> 至少给两条实现路径，其中一条要比你原本打算做的更有雄心。列出各自代价、局限、以及选便宜那条会失去什么。不要直接开始写代码。

### A4. 禁止自评（用于涉及正确性的任务）

> 不要用"逻辑上成立""应该没问题"作为完成依据。用真实数据跑一遍，给出可复现的验证步骤和结果；无法验证的部分明确标注为未验证。

### A5. 对抗性检验（用于既有假设、历史遗留结论）

> 我们一直认为 <假设>。请从原始数据/原始代码出发，主动找证据推翻它，而不是找证据支持它。如果推翻不了，说明试过哪些方法。

### A6. 跨领域视角（用于方案设计、评审）

> 把这件事用动词重新描述一遍，再据此引入 2–3 个表面用不到的专业视角（含一个对手方视角，如攻击者/做空者/挑刺评审）。让每个视角实际做它会做的动作，并改变产出；不要只换措辞扮演角色。

### A7. 交付后追问（一句话，任何时候可用）

> 如果更有雄心，下一步是什么？代价是什么？

## B. 智能体侧：任务重写协议

收到 L2 级任务时，按以下顺序处理，再执行：

```
输入：用户的原始指令
1. 字面目标：______
2. 结果目标（做完后用户的下一步）：______
3. 上层目标（彻底解决后什么会消失）：______
4. 级别判定：L0 / L1 / L2，理由：______
5. 路径 A（最省事）：做法 / 代价 / 局限
6. 路径 B（更有雄心）：做法 / 代价 / 多解决了什么
7. 选择与理由：______（若选 A，写明放弃了什么）
8. 外部验收标准：______
9. 需引入的其他视角及其具体动作：______（无则写无）
10. 若 2 与 1 差距大到改变任务性质 → 先向用户确认，不擅自扩范围
```

执行后交付时附：

```
【验证】实际运行的外部验证及结果；未验证项明确标注
【更进一步】① …（解决什么/代价）② …（可选）
```

## C. 组合示例

原始指令："修一下同步脚本的路径问题。"

浅执行：改一行路径，跑通，结束。

按本协议：
- 字面：修路径。结果：让同步在 macOS 上可用。上层：这类环境差异导致的同步失败不再出现，也不需要每次换机器就改代码。
- 路径 A：改这一处硬编码。代价 1 分钟；局限：下一处硬编码、下一台机器还会犯。
- 路径 B：统一路径推导入口 + 启动时环境自检（依赖目录、端口、配置是否就绪），失败时给出具体缺失项而非堆栈。代价约半小时；多解决：同类问题一次性消失，且报错可读。
- 验收：在 macOS 上真实跑一次同步；模拟缺失目录，确认报错指出缺失项；确认 Windows 路径推导未被破坏。
- 交付附录：更进一步可把环境自检抽成所有脚本共用的启动模块。
