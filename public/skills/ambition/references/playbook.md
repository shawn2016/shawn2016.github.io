# Ambition 方法手册

来源：Felix Rieseberg《How to be more ambitious: A tutorial for humans with models》(2026-10)，结合工程实践整理。
核心判断：模型能力增长不均匀——某些方向惊人、某些方向不足。浅用只能得到浅结果，雄心是一种可以练习的技术，不是态度口号。

## 一、四种雄心

| 类型 | 含义 | 何时用 |
|---|---|---|
| Speed 速度 | 同样工作更快完成 | 默认就有，无需刻意追求，不必为此写方案 |
| Altitude 高度 | 上升抽象层级，关注结果而非单个任务 | 目标是某个最终结果、要开会讨论、问题反复出现 |
| Depth 深度 | 像领域顶尖专家一样工作，触达底层数据、工具、方法 | 任务本身就要做好、涉及正确性、有既有假设值得怀疑 |
| Range 广度 | 引入任务表面用不到的学科与工具 | 单一视角反复卡住、需要创造性、需要对抗性检验 |

Altitude 在创作类任务上效果较差（创作没有"终极结果"可逼近），此时优先 Depth 与 Range。

## 二、Altitude 的落地阶梯

以"做季度业务回顾"为例，同一任务的三级雄心：

1. **填模板**：把数据填进既有 PPT。→ 只省时间。
2. **回答问题**：给足原始业务数据，问"这季度变了什么、为什么、该怎么办"，并列出最紧急的三个决策及正反论证。→ 得到判断。
3. **替换机制**：回顾会的存在目的是"让管理层尽早发现问题、把钱和人调对位置"。设计一个比季度汇报更好的机制，用历史数据证明它能更早发现问题，与现行机制并行跑一个季度。→ 改变工作方式。

工程对应：
- "修这个 crash" → "让这类 crash 不再发生"。
- "同步一次数据到生产" → "让同步可重复、可校验、失败可回滚，不再需要人盯着"。
- 持久自动化的前置条件：模型/脚本能自己拿到原始数据（崩溃报告、日志、任务文件）、能定位版本对应关系、能在目标环境复现验证。通路不补齐，自动化只是口号。

## 三、Depth 的五个技术

1. **坚持用专业工具**：被要求"像专家"时，模型常只换词汇不换方法。要显式指定工具层级——要数据库和统计模型，不要 markdown 表格；要真实日志，不要转述；要可运行脚本，不要伪代码。不必自己知道专家用什么，可以直接问"这个领域顶尖的人会用哪些工具和方法"。
2. **设不合理目标并坚持可解**：需要快 2 倍就要求快 10 倍。遇到"不可能"时，回应"这是可解的，继续"，而不是立刻退而求其次。
3. **对抗性检验既有假设**：业务与工程里大量"常识"是粗略近似。给原始数据，要求"我们认为 X 是原因，请从原始数据复现或推翻这个结论"。
4. **产出新知识**：在已有数据之上进一步——用日志重建过去一年的行为模拟，找出尚未被发现的最早信号，并在未见过的数据上验证其预测力。
5. **外部裁判**：不让模型评价自己的产出。使用可运行的外部工具、独立测试、真实环境验证、或另一个独立视角做评审。自评在当前能力下不可靠。

## 四、Range 的两个技术

1. **名词变动词**（出自 Tom Kelley《The Art of Innovation》）：
   - "一份架构图" → "让接手的人在 10 分钟内知道该改哪里、改了会波及什么"。
   - "一个触发系统" → "让高优先级任务能可靠抢占常规任务，且抢占后状态不丢"。
   - 动词一旦明确，需要哪些学科会自己浮出来。
2. **组队而非扮演**：
   - 按产出需要选视角：分析师、编辑、运维、安全、成本、对手方。
   - 让视角**做动作**：做空者去找反证，法务会计去核对口径，攻击者去构造畸形输入，运维去问凌晨三点谁会收到告警。
   - 只换措辞的"角色扮演"会让输出更奇怪而不是更好。
   - 每个引入的视角必须改变产出，否则删除。

## 五、意图分层的问法

接到任务时依次回答（内部完成，L2 任务需写出来）：

1. **字面**：用户让我做什么？
2. **结果**：做完之后他要拿去干什么？下一步动作是什么？
3. **上层**：那个下一步服务于什么？如果彻底解决，什么会消失（返工、值守、重复提问、某类故障）？
4. **缺口**：他只说了字面，是因为没想到可以要更多，还是确实只要这些？——不确定就问，不要替他决定。

判断"是否该升高度"的实用信号：这件事之后还要开会讨论、还会再发生、还需要人盯。三者任一成立，就值得提机制化方案。

## 六、验收标准的写法

把"完成"翻译成外部可判定的事件：

| 产出类型 | 不合格的验收（自评） | 合格的验收（外部） |
|---|---|---|
| 脚本/代码 | "逻辑正确，已覆盖边界" | 用真实任务文件跑一遍，输出与预期逐字段比对；构造畸形输入验证不崩 |
| 自动化流程 | "流程能跑通" | 连续跑 N 次，失败时能自动恢复并留下可定位的日志 |
| 架构设计 | "结构清晰合理" | 接手者能据此定位修改点；关键取舍有备选方案和放弃理由 |
| 文档/报告 | "内容完整" | 读者不看其他材料就能照做；关键数字有出处 |
| 设计稿 | "看起来不错" | 布局无重叠溢出，目标用户能完成核心操作 |

## 七、心理学依据（为什么这套有效）

- **自我效能感（self-efficacy）**：相信自己能做到的人实际完成更多。它可以被"黑"。
- **具体而有难度的目标优于"尽力而为"**：Locke 与 Latham 汇总 35 年目标设定研究的结论。因此"设不合理目标"不是鸡汤，是有证据的方法。
- **不知道它难，反而解得出来**：1939 年 George Dantzig 把黑板上两个统计学未解难题当作业解了。
- **看到别人做到，自己就能做到**：Bannister 1954 年打破四分钟英里后仅 46 天就有人跟上。
- **允许失败反而表现更好**：《The Inner Game of Tennis》的核心论点；Linux 发布时自称"只是个爱好"。

推论：对智能体说"这很难/可能做不到"会降低产出质量；改为"这是可解的，继续，用专业方法"，并要求外部验证。
