先说一个绕不开的事实。

你想让 AI 帮你发小红书、看数据、回评论。查了一圈会发现：小红书没有给你一个能发布内容的开放接口。官方开放平台面向的是广告投放和品牌合作，不是「让程序替我发一篇笔记」。

于是大多数人往两个方向走。一是逆向接口，抓包、还原签名、模拟请求——快，但平台一改签名就全废。二是老老实实手动发。

[xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp) 走了第三条：不去碰接口，直接开一个真实浏览器，用人的方式点页面——鼠标走曲线、点击有停顿、输入有延迟。AI 说「发一篇笔记」，它就像个坐在这台机器前的人，登录、点创作中心、填标题、传图、发布。

这篇想说清楚一个判断：**当一个平台不给你接口，自动化的信任就不再来自「授权」，而来自「你以一个真人身份登录」——你装得越像人，能力越接近真人，但整个能力的地基也越脆弱。** 地基是那个随时会过期、会被踢下线的登录态。

[xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp) 是这条判断的一个极端样本。2025 年 8 月 3 日建库，到 2026 年 11 月 17 日约 17,156 star、2,530 fork、111 个开放 issue，Apache-2.0 协议。语言分布以 Go 为主（约 42.8 万字节），Python 约 9.5 万字节。41 位贡献者，但主作者 xpzouying 一人 304 次提交——这是个高度依赖单个维护者的项目。

## 信任不来自授权，来自你扫码的那一下

传统 API 集成的信任是一次签发的密钥：平台给你 token，你拿 token 调接口。密钥只要不泄露，就一直有效。

这里没有这套东西。第一次用，得先跑登录工具，弹出二维码，用手机 App 扫码。登录态被存成 `~/.xiaohongshu/cookies.json`，之后每次启动服务都读这个文件。README 里那句提示把代价说透了：**同一个账号不允许在多个网页端登录**，你登录了 MCP，再在浏览器网页端登一次，就会把 MCP 的登录态踢掉。

这句话定义了整套能力的性质。信任不是你「申请」来的，是你「占住」的——占住一个真人会话，且不能和别人共用。cookie 过期了要重新扫，被踢下线了要重新扫，平台要实名认证了还得先实名（README 特别说明：未实名的新号触发的实名提醒不是封号，不用 MCP 也会遇到）。

这跟软件 KVM 里「配对那一刻建立信任」是同一个结构：不靠中心签发，靠一个一次性的、带物理约束的动作。只不过这里的动作是扫码，约束是「这台机器上的这个浏览器，此刻就是这个账号的登录终端」。

## 装成一个人，要装到什么颗粒度

信任建立之后，剩下的工作全是「别被认出来是机器」。这块是项目最值得拆的部分，也是判断成立的技术前提。

它用的是 `go-rod`（v0.116.2）驱动真实浏览器，配了 `stealth`（v0.4.9）做反自动化检测。但真正决定像不像人的，是 `humanize` 这个包：

- **鼠标走曲线，不走直线。** `moveMouseCurved` 让指针沿弧线移动到目标，而不是瞬移或走一条笔直的线——真人移动鼠标不会是完美的直线。
- **操作之间插入随机延迟。** `Delay(ctx, action)` 按动作类型从一个分布里采样等待时间，点击、输入、导航各有各的节奏，不是固定 sleep。
- **按下和松开之间有停顿。** 鼠标按下后先 `time.Sleep` 一段随机时间再松开，模拟真人点击的按住时长。

这套拟人化不是装饰。平台风控看的就是这些——鼠标轨迹、操作间隔、点击节奏。装得不像，轻则弹验证码，重则限流封号。

更有意思的是它怎么处理「被认出来」。`xiaohongshu/page_check.go` 里区分了两条路径：`/website-login/captcha` 是需要手机 App 扫码的身份核验，`/website-login` 是登录态失效。代码注释写明：判断只看路径、不看查询串，因为登录页会带 `redirectPath=/website-login/captcha` 这样的参数，整条 URL 匹配就会把登录页误判成验证页。命中不同路径，返回不同错误——调用方能明确知道「该去扫码验证」还是「该重新登录」，而不是拿到一句含糊的超时。

这是成熟自动化和玩具的分界线：**它假设自己一定会被风控拦，把「识别拦截并给出明确退出信号」当成一等公民**，而不是假装平台永远不会发现。

这个判断的成立条件也很清楚：只适合「量不大、像真人」的场景。作者自己写，按实操小红书每天发帖量约 50 篇。一旦你要规模化——多账号、大规模铺量——「装成一个人」这件事本身就和规模冲突。一个人一天发 50 篇已经是极限，一百个号同时动，再像人也是机器。

## 方法论之下，功能是怎么长的

功能不按模块列表堆，按「一次真人会话的动作序列」长。这是判断的延续：既然装成人，那工具就该按人干活的先后顺序排列。

1. **先证明还活着。** `check_login_status` 查登录态，`get_login_qrcode` 取二维码，`delete_cookies` 重置登录。每次动手前先确认会话有效。
2. **再像人一样看。** `list_feeds` 拿推荐流、`search_feeds` 搜关键词、`get_feed_detail` 看帖子详情、`user_profile` 看主页。注意详情和主页都要 `feed_id` 加 `xsec_token` 两个参数，而 token 只能从 Feed 列表或搜索结果里拿——这个设计逼你「先列表后详情」，正好像真人一样先刷到再点进去。
3. **然后才动手。** `publish_content` 发图文、`publish_with_video` 发视频、`post_comment_to_feed` 发评论、`reply_comment_in_feed` 回复、`like_feed` 点赞、`favorite_feed` 收藏。点赞收藏都带状态检测——已点赞就跳过，避免重复操作露馅。
4. **回头看反应。** `get_unread_count`、`list_notifications`、`reply_notification`、`like_notification` 处理通知和互动回响。

同一个能力有两套入口：MCP 工具给 AI 客户端调，HTTP API（`/api/v1/*`，服务在 `18060` 端口）给程序直接调。两套入口指向同一批操作，只是调用方不同。

版本节奏能看出这套「像人」的工程有多依赖持续维护。11 月 3 日到 10 日一周内连发 v2.7.2、v2.7.3、v2.7.4：v2.7.2 修的是话题标签点击失效（编辑器重绘导致点不中），v2.7.3 修的是搜索时被延迟重定向到验证页的诊断，v2.7.4 加了图文发布时 @ 用户。这些不是功能迭代，是平台页面一变、拟人化操作就得跟着改的补丁。

## 从零跑通，大概要几步

按使用顺序记一遍，每步都对着前面的判断。

1. **先装。** 三条路：从 Releases 下预编译二进制（只支持 macOS Apple Silicon、Windows x64、Linux x64，Intel Mac 和 Linux ARM64 暂不支持）；或源码编译 `go run .`；或 Docker（`docker compose -f docker/docker-compose.yml up -d`）。首次运行会自动下载无头浏览器，约 150MB，网络要通。
2. **登录，把登录态占住。** 跑登录工具 `./xiaohongshu-login-darwin-arm64` 扫码，cookie 存到 `~/.xiaohongshu/cookies.json`。这一步之后，别再在别的网页端登这个号。
3. **起服务。** `./xiaohongshu-mcp-darwin-arm64` 默认无头；想看浏览器界面用 `-headless=false`。Docker 版地址是 `http://127.0.0.1:18060/mcp`。需要图形界面排查现场，用 noVNC 版（`docker/novnc`），打开 `http://127.0.0.1:6080/vnc.html`，但只限本机或 SSH 转发，别暴露公网。
4. **接上 AI 客户端。** Claude Code 用 `claude mcp add --transport http xiaohongshu-mcp http://localhost:18060/mcp`；Cursor、VSCode、Open Code 都是填这个 URL 的 HTTP 型 MCP 配置。
5. **验证。** `npx @modelcontextprotocol/inspector`，连 `http://localhost:18060/mcp`，点 List Tools，能看到那十几个工具就通了。
6. **进阶两件事。** 要代理设 `XHS_PROXY`（支持 HTTP/HTTPS/SOCKS5，日志自动隐藏认证信息）；生产环境开鉴权 `AUTH_TOKEN=xxx`，客户端要带 `Authorization: Bearer xxx`——命令行 `-token` 参数会被进程列表看到，部署时用环境变量。

非技术同学别折腾这套部署，同作者另有浏览器插件版 [x-mcp](https://github.com/xpzouying/x-mcp)（2025 年 10 月建库，约 498 star），装在 Chrome/Edge 里零配置，跑在本地网络，规避了服务器 IP 被风控的风险，号称解决 90% 的部署报错。

## 同类方案怎么选

对比不按功能打分，按前面那条判据：**信任从哪来、装人装到哪一层、地基塌了谁来修**。

| 方案 | 信任从哪来 | 装人 / 接口 | 平台 | 成本 | 塌了谁修 |
|---|---|---|---|---|---|
| 官方开放平台 | 平台签发的授权 | 正规接口，无需装人 | 官方支持 | 需资质、受权限限制 | 平台保证兼容 |
| 逆向签名 / 私有 API | 抓包还原的签名 | 伪装成客户端请求 | 随平台变 | 免费，自维护 | 自己，签名一改就废 |
| xiaohongshu-mcp | 自己扫码的登录态 | 真实浏览器 + 拟人化操作 | Mac ARM / Win / Linux | 免费开源，自部署 | 作者 + 社区，页面一变要补丁 |
| x-mcp 浏览器插件 | 自己浏览器的登录态 | 真实浏览器，无服务器 | Chrome / Edge | 免费，零配置 | 作者 |
| 纯手动 | 人自己登录 | 真人本尊 | 不限 | 时间成本 | 不需要 |

按成立条件套自己的场景：

- 要的是合规、稳定、有 SLA：走官方开放平台，接受它的权限边界，别折腾自动化。
- 只做小批量、自己一个号、要接进 AI 工作流：xiaohongshu-mcp 正合适，能力最接近真人。
- 不懂部署、就在自己电脑上用、怕服务器 IP 被风控：换 x-mcp 插件版。
- 要大规模多账号铺量：这套「装成一个人」的路线从根上不成立，规模是它的敌人，别在这条路上加码。

## 边界和代价

- **地基随时会塌。** 整套能力压在一个会过期、会被踢的登录态上。多网页端登录会互踢，cookie 过期要重扫，平台加验证要扫码。这不是 bug，是这条路线的固有成本。
- **风控是持续战，不是一次性投入。** 11 月一周三版修的全是页面变化导致的点击失效和重定向误判。平台改一次前端，拟人化操作就可能失灵。
- **项目高度依赖一个人。** 41 位贡献者听着热闹，但主作者 304 次提交，机器人 55 次（多是贡献者名单和文档的自动更新），真正的代码贡献集中在少数人手里。111 个开放 issue 也是个不小的存量。
- **平台规则风险自担。** README 明确写了禁止引流、纯搬运，这些是官方重点打击对象；并声明项目基于学习目的，禁止一切违法行为。作者说原项目稳定运行一年多没封过号，但「没封过」不等于「不会封」。

## 本次采集学到的判断

当一个平台不给接口，自动化的信任就从「授权」转移到「登录态」——你占领一个真人的会话，能力上限就是这个真人的上限。判断这类工具，别数它封装了多少功能，看两件事：它把「像人」做到什么颗粒度，以及被认出来时它是硬闯还是给出明确退出信号。规模是这套路线的天敌：能用一个人解释的操作量，才是它真正成立的地方。
